# frpdeck 1.2.0

`1.2.0` focuses the CLI on the normal instance workflow while preserving the existing supported command paths. It also tightens operator-facing failures, makes diagnostics resilient to broken configuration, and removes ambiguous proxy deletion behavior.

## Highlights

- Top-level help now groups commands into common workflow, preflight/advanced deployment, runtime control, maintenance/diagnostics, and integrations/inspection panels.
- Proxy help now separates common operations, import/inspection, and permanent deletion.
- Expected configuration, filesystem, release lookup, and operational failures are concise stderr messages rather than Python tracebacks. Existing JSON commands continue to emit a single parseable envelope on stdout.
- `status` retains its partial-status behavior even when instance configuration is damaged.
- `doctor` reports invalid instance configuration as a failed check while continuing system checks.
- MCP wrapper installation validates the bound instance before creating files or audit records, and its default guidance is local-first.
- The unused legacy status service module has been removed.

## Upgrade Note

This release includes intentional Beta-stage breaking changes:

1. `frpdeck proxy remove NAME` now permanently deletes the proxy definition from `proxies.yaml`.
2. Use `frpdeck proxy disable NAME` when the definition must remain present with `enabled: false`.
3. The former `proxy remove --hard` option has been removed; `remove` has only the permanent-delete meaning.
4. The MCP `remove_proxy` tool no longer accepts a `soft` parameter. Bound mode accepts only `name`; generic mode accepts `instance_dir` and `name`.
5. `frpdeck doctor` now diagnoses the current-directory instance and the system by default. Use `frpdeck doctor --system-only` when no instance checks are wanted.
6. MCP wrapper installation no longer has a built-in SSH host. Pass `--ssh-host HOST` explicitly to print remote SSH examples and guidance.
7. `mcp install-stdio-wrapper` now requires the target directory to contain a valid, loadable `node.yaml` before it writes the wrapper or audit data.

Regenerate MCP client configuration examples if they previously depended on an implicit remote host. Existing generated wrapper files do not embed that host and therefore do not need content changes solely for this migration.

## Workflow Clarifications

The normal deployment flow is now documented as:

```text
init → edit configuration and secrets → apply → status
```

`validate` remains an optional read-only preflight, `render` only updates `rendered/`, and `sync` only copies the current rendered snapshot into `runtime/config`. Client `reload` uses the frpc control/web endpoint without restarting systemd; `restart` restarts the systemd service with current runtime config. Use `apply` for a complete deployment.

`check-update` and `upgrade` operate on the managed FRP binary. They do not update the frpdeck Python package.
